# rust-mirror-gui 0.4.2: lower CPU use while working, large crate previews

Released 2026-11-15. A patch release. While an operation ran, the window
redrew continuously, which used several processor cores on machines that
draw in software (Remote Desktop, no GPU) and slowed the operation itself.
Large crate previews failed in the window. Both are fixed, and the built-in
engine is now rust-mirror 0.5.1.

## Changes

- **Fixed: high CPU use while an operation runs.** The window redrew for
  every line of worker output, and a details table that changed size on
  every redraw asked for another redraw, so it redrew continuously during a
  download. The window now redraws once a second while an operation runs,
  so the status and the "last event" counter still update every second.
  Input still redraws at once, and so do the end of an operation, an error,
  a retry wait and the stalled warning. The crate preview table and the
  activity log lay out only the rows in view.
- **Fixed: large crate previews failed in the window** with "event line
  exceeds 1 MiB". A preview's result grows with the catalog (about 4 KB per
  crate version); the window now accepts up to 64 MiB.
- **Built on rust-mirror 0.5.1.** Crates that crates.io lists more than once
  with only different build metadata (for example `ndk-sys 0.4.0`, needed
  by eframe) no longer make the preview fail when none of those versions is
  selected; the preview shows a warning naming the crate and versions.
- The crate preview table has fixed columns: long flags and reasons end in
  "…", with the full text on hover. It lists up to 10,000 versions (was
  400). Long lines in the activity log scroll sideways instead of wrapping.
- **Diagnostics:** set `RUST_MIRROR_GUI_FRAME_LOG` to a file name, and the
  app writes once a second how often the window redrew and why.
  `RUST_MIRROR_GUI_PRESENT_MODE` (`fifo`, `mailbox`, `immediate`,
  `auto_vsync`, `auto_no_vsync`) picks the swap-chain present mode.

## Upgrade

```sh
cargo install rust-mirror-gui --version 0.4.2 --locked
```

- Rust 1.95 or newer is still required.
- The built-in engine is now
  [rust-mirror 0.5.1](https://crates.io/crates/rust-mirror/0.5.1). Catalogs,
  mirrors and settings are unchanged.
- Windows still renders with Direct3D 12 unless `WGPU_BACKEND` is set.
- No new dependencies.

## Validation and limits

Evidence is in the
[Remote Desktop record](https://github.com/rustcommons/rust-mirror-gui/blob/main/docs/evals/2026-11-15-remote-desktop.md).

- **CPU while downloading crates**, inside real Remote Desktop sessions
  without a GPU (window process only, % of one core, same download for
  both versions):

  | Platform | 0.4.1 | 0.4.2 |
  | --- | --- | --- |
  | Linux, xrdp, Mesa llvmpipe/lavapipe | 317% | 14.4% |
  | Windows, RDP, Direct3D 12 on WARP, Intel Xeon Platinum 8370C | 190.3% | 8.6% |
  | Windows, RDP, Direct3D 12 on WARP, AMD EPYC 7763 | 311.4% | 66.2% |

  Windows numbers are from one run with the processor recorded; earlier
  runs ranged 4.5–14% and 62–130% for 0.4.2, and 165–327% for 0.4.1. Idle
  is 0%.
- **Known limit, Windows without a GPU on some processors:** Windows'
  software renderer (WARP) took about 0.6–0.9 s of CPU per frame on the
  AMD EPYC 7763 test machines, against about 45–80 ms on the Intel Xeon
  ones. On those machines the window uses most of one core (under a quarter
  of a 4-core machine) while an operation runs, even at one redraw a
  second. That is over the test plan's 25% of one core.
- **Remote Desktop scenarios** on Windows Server 2022 and 2025 (loopback
  RDP, FreeRDP client) and on Linux with xrdp all pass:
  - launch under 10 s;
  - a crate sync with live status, Stop and Resume;
  - disconnect mid-sync and reconnect, with the sync finished;
  - reconnect at another resolution and at 150%;
  - minimizing the client;
  - starting on the console and taking over through RDP (Windows).
- **Tests:** new automated tests cover a 3 MiB result line, and the layout
  checks still pass at 900×600 with 100%, 125% and 150% scaling.
- **Not tested:** macOS; Remote Desktop from another machine or with
  Microsoft's client (`mstsc`); screen readers.
