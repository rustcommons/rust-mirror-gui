# rust-mirror-gui 0.5.4: clearer crate previews and freshness ages

Released 2026-11-22. This patch release makes large crate previews easier
to read. The built-in engine stays at rust-mirror 0.6.1.

## Changes

- **Grouped metadata warnings:** an upstream index backfill can affect
  thousands of crate versions. The preview now shows one summary with
  distinct version and crate counts and the changed field names when
  available. A single affected version still gets a plain line.
- **Details stay out of the way:** **Show details** starts closed and
  groups versions by crate. It shows at most 200 crate headings/version
  rows, then the number of remaining versions. The summary and bounded
  details are prepared when the worker report arrives, so each frame does
  not regroup or copy the full warning list.
- **Accurate metadata wording:** crate files are unchanged; the new mirror
  serves the updated index entries. The display does not change the frozen
  plan or its identity.
- **Readable freshness ages:** the crate-index banner and release-list
  status use phrases such as "8 days ago" and "3 hours old". Ages below
  six hours include minutes when needed. Live job timers keep their
  existing format.
- **Repository:** record the 0.5.3 publication and the first complete phase 2
  run, and point the public download check at v0.5.3. This is documentation
  and verification maintenance.

These notes come from the dated
[CHANGELOG entry](https://github.com/rustcommons/rust-mirror-gui/blob/main/CHANGELOG.md).
No engine or dependency update is included. Catalogs, settings and event
protocol 1 remain compatible.

## Upgrade

Download your platform's archive from the
[GitHub Release](https://github.com/rustcommons/rust-mirror-gui/releases/tag/v0.5.4),
or install with Rust 1.95 or newer:

```sh
cargo install rust-mirror-gui --version 0.5.4 --locked
```

The release layout is unchanged from 0.5.3: the `.crate`, four platform
archives, CycloneDX SBOM, one `SHA256SUMS` listing those six payloads, and
one signed `.intoto.jsonl` bundle (eight assets). The bundle signs the six
payloads and `SHA256SUMS` and is not itself listed in that manifest.

Use the strict verification command in each archive's `README.txt`:
signer workflow `build-binaries.yml`, signer and source digests pinned to
the release commit, and GitHub-hosted runners only. The
[verification guide](https://github.com/rustcommons/rust-mirror-gui/blob/main/README.md#download-a-prebuilt-binary)
also explains the attached bundle and SBOM checks.

## Validation and limits

The [validation record](https://github.com/rustcommons/rust-mirror-gui/blob/main/docs/evals/2026-11-22-v0.5.4-validation.md)
separates completed local checks from pending CI. Before merge, the release
PR must have a green exact-head Trusted publishing dry run with all four
targets, the crate package/audit/install, Windows capture, fontless
AlmaLinux 8 and Ubuntu 20.04 launches, six checksum entries and zero
deprecation annotations. A dry run does not sign or publish.

After merge, the owner waits for successful CI on main, pushes the tag and
approves Trusted Publishing. The pipeline publishes the crate, creates the
GitHub Release and verifies the public assets. A publication record follows.

Known limits are unchanged: screen readers, the macOS window and Wayland
are untested; software rendering can use about 66% of one core on AMD EPYC
during downloads; the binaries are not code-signed. See
[0.5.0's limits](https://github.com/rustcommons/rust-mirror-gui/blob/main/docs/releases/v0.5.0.md#validation-and-limits).
