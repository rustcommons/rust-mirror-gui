# rust-mirror-gui 0.3.0 validation record (2026-11-13)

Scope: the crate mirroring pages, built on rust-mirror 0.4.0 from crates.io
(checksum `c3af7381321b8dd1d780e6d519ca0a7933285165ad413bca55ce8a3efca96451`,
release merge `3f815fe`). Development first used a git pin to rust-mirror main
`0a6102b`. All runs and screenshots below were then repeated with the
crates.io 0.4.0 build (top bar "rust-mirror 0.4.0 built in").

Environment:
- Debian 12 aarch64, Rust 1.99.1 (CI and local checks also on Rust 1.95.0).
- Xvfb with Mesa lavapipe, no GPU.
- Real network access to crates.io.
- All outputs under `/tmp`. No Rustup or Cargo home was used as output, except
  an isolated throwaway `CARGO_HOME` for the client test. No Nexus server.

## Automated

`cargo test --all-features` runs 19 unit tests and 15 process tests. New in
0.3.0:
- crate events: concurrent artifacts are marked complete only by
  `artifact_complete`, not by the next artifact starting; `crate_summary`; a
  `retry` with `kind: rate_limited` produces the "slow down" message;
- crate sync arguments: a preview never approves; approval carries
  `--approve-plan`, `--resume` and `--previous`, and does not re-estimate
  sizes;
- real worker, offline: catalog JSON is written as TOML and loaded back; paste
  accepts `serde` and refuses a path dependency with kind `path` on line 3.

Earlier worker-only runs on the git pin (an early cancel before downloading,
then `--resume`) are superseded by the GUI runs above.

**Found and fixed during testing:**
- With concurrent downloads, the old "next artifact means the previous one is
  done" rule is wrong. The app now uses `artifact_complete` once the backend
  sends it.
- `crate_summary.transferred_bytes` counts bytes across resumes, so the app
  now shows files done and reused bytes, and takes this run's new download
  from the final report.
- The crate progress bar now shows files verified out of the total, rather
  than the sum of the files started so far.
